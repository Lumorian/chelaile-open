# 逆向分析报告：车来了 7.6.8

> 分析时间：2026-11-08 · 分析对象：`车来了.apk`（Android）· 分析方式：纯静态 + 协议黑盒验证
>
> 本文记录**结论与证据**，包含可复现的命令。所有操作均在本地副本上完成，未对线上服务做任何写操作或压力测试。

## 0. TL;DR

| 问题 | 结论 |
| --- | --- |
| 加固方式 | **娜迦（SecNeo）DexHelper**：`Application` 被替换为 `com.secneo.apkwrapper.AW`，dex 体内嵌 62 MB 加密载荷，运行时由 `libDexHelper.so` 解密并 `mmap` 成内存 dex |
| 能否直接反编译 | 不能。apktool/jadx 只能看到 7 个壳类；真实业务代码（约 62 MB dex）是加密的 |

## 2. 静态侦察：这是一个被加固过的壳

### 2.1 Manifest 的破绽

`AndroidManifest.xml` 里有两个字段几乎等于自报家门：

```xml
<application
    android:name="com.secneo.apkwrapper.AW"
    android:appComponentFactory="com.secneo.apkwrapper.AP"
    ...>
```

正常 App 的 `Application` 是自己的类；这里是 `com.secneo.apkwrapper.AW`——**娜迦（SecNeo）DexHelper** 的入口壳。

### 2.2 dex 里只有 7 个类

```bash
unzip -o 车来了.apk classes.dex -d /tmp/x
cd out/apktool && find smali -name '*.smali' | wc -l   # 7
```

```
com/secneo/apkwrapper/AP.smali
com/secneo/apkwrapper/AW.smali
com/secneo/apkwrapper/CP.smali
com/secneo/apkwrapper/H.smali
com/secneo/apkwrapper/H$a.smali
com/secneo/apkwrapper/a.smali
com/secneo/apkwrapper/b.smali
```

真实的 `classes.dex` 有 **62,191,276 字节**，却只定义 7 个类——说明体积全在`数据段`里，即被加密的业务 dex。

### 2.3 native 层

`lib/arm64-v8a/` 里的关键库：

| 库 | 大小 | 作用（推断/证据） |
| --- | --- | --- |
| `libDexHelper.so` | 1.25 MB | 娜迦解密器主体，**已 strip**，无导出符号表；无 AES S-box，但含 TEA 常量 `0x9e3779b9` |
| `libDexHelper-x86.so` | — | 实为 **x86-64** ELF（命名与架构不符，常见于加固厂商的打包脚本） |
| `libdexjni.so` | 2.2 MB | dex 加载 JNI 桥 |
| `libzxprotect.so` | — | 另一层保护（反调试/完整性校验） |
| `libtiny_magic.so` | — | 体积很小的“魔术”库，疑似反调试探针 |
| `libmmkv.so` / `libmsc.so` | — | 腾讯 MMKV 存储 / 讯飞语音 |
| `libAMapSDK_MAP_v10_0_1000.so` / `libBaiduMapSDK_base_v7_5_8.so` | — | 高德 / 百度地图 SDK |
| `libcqffmpeg.so` | — | 音视频（语音播报） |


## 3. 加固载荷的物理结构（本文最硬的部分）

### 3.1 在文件里定位

壳 dex 的有效数据到偏移 `0x568C` 结束，紧接着是一段自定义结构：

```
偏移      内容
0x568C    01 00 00 00              ← 块数 = 1
0x5690    14 A0 B4 03              ← 总长度 0x03B4A014（62,169,108）
0x5694    08 00 00 00              ← 名字长度 8
0x5698    "dexdata0"               ← 块名（ASCII）
0x56A0    00 A0 B4 03              ← 块长度 0x03B4A000（62,169,088）
0x56A4    <载荷起点，文件偏移 22180>
...
文件末尾  "fdex"                   ← 4 字节尾部魔数
```

```bash
python3 - <<'PY'
data = open('/tmp/x/classes.dex','rb').read()
print(hex(len(data)))                       # 0x3b4a9a4
i = data.find(b'dexdata0')
print('dexdata0 @', i, hex(i))              # 22160 / 0x5690+8
print(data[0x568c:0x56a4].hex())
print(data[-8:])
PY
```

### 3.2 载荷的熵分布

把 62 MB 载荷按 4 KB 分块算 Shannon 熵，得到非常典型的“加密头 + 明文尾”结构：

| 区域（相对载荷起点） | 熵 | 判读 |
| --- | --- | --- |
| 0 – ~1.9 MB | ≈ 7.99 bit/byte | **加密区**：dex 头、字符串索引、类定义都在这里，被整体加密 |
| ~2.0 MB 之后 | 4.5 – 6 bit/byte，可见 `Lcom/…;`、`Ldev/xesam/…`、`KotlinDebug` | **明文区**：字符串池（string_data_item）没有被加密 |
| ≈5–7 MB / 16–17 MB / 26–28 MB / 37–38 MB / 50–52 MB | ≈ 0.3 bit/byte（`0f 2d 1e 3e` 循环） | 填充区，非合法 dex 内容 |
| ≈13.6 / 16 / 27 MB | — | 出现「偏移 + 计数」三元组，疑似分块表 |

```bash
python3 /tmp/tools/profile.py    # 逐块熵 + 直方图
python3 /tmp/tools/survey.py     # 魔数/填充/元组扫描
```

**关键观察**：全文件中，除偏移 0 处的壳 dex 外，**没有任何 `dex\n035` 魔数**。也就是说业务 dex 的头部（及其 `class_defs` 指向的代码项）是加密的，只有字符串常量以明文散落在载荷中。这就是我们能“白嫖”到全部字符串、但拿不到代码的原因。

### 3.3 为什么没有继续硬脱壳

可行路径与代价：

| 方案 | 代价 | 结论 |
| --- | --- | --- |
| 静态还原 SecNeo 解密算法 | 需要逆向 1.25 MB 的 strip 过的 ARM64 汇编（含 VM/混淆），或复现其 JNI 调用约定；周期以周计，且版本一升级就失效 | 放弃 |
| Frida gadget 注入 + dump 内存 dex（如 `strazzere/secneo-gadget`） | 需要 **真机**（APK 只有 arm64-v8a/armeabi-v7a，本机无 KVM 可用 ARM 模拟器，x86 库又是坏的） | 环境不具备 |
| **改用 H5 接口**（本项目选择） | 需要重新摸清协议，但接口是公开可见的 HTTPS，且**功能面完全一致** | ✅ 采纳 |

> 结论：对于“做一个等价的开放客户端”这个目标，脱壳的**边际收益极低**——业务逻辑（线路、到站、换乘）本来就在服务端；客户端只是渲染。真正需要逆向的是**协议**，而协议可以通过 H5 端点黑盒验证。

## 5. 协议还原：从黑盒到可运行实现

### 5.1 抓包形状

任何 `web.chelaile.net.cn/api/…` 接口的响应都长这样：

```
**YGKJ{"jsonr":{"status":"00","errmsg":null,"data":{ ... }}}YGKJ##
```

- 前缀 `**YGKJ` 与后缀 `YGKJ##`：网关防 JSONP 劫持的包裹（来源不明，可能对应 "阳关科技"?）；
- `jsonr.status`：`"00"` 成功，其它为错误码。

### 5.2 公共参数（缺一不可）

| 参数 | 值 | 说明 |
| --- | --- | --- |
| `s` | `h5` | 端类型 |
| `v` | `9.1.2` | H5 版本号 |
| `vc` | `1` | version code |
| `src` | `wechat_shaoguan` | 渠道（韶关微信渠道；换成别的值多数接口仍可用） |
| `userId` / `h5Id` | `browser_xxx` | 匿名用户标识，随便给 |
| `sign` | `1` | 固定值 |
| `cityId` | 城市 ID | 见城市表 |
| `geo_lat` / `geo_lng` / `lat` / `lng` | 坐标 | 两套坐标都传，值相同即可 |
| `gpstype` | `wgs` | 坐标类型 |

漏参数时服务端返回 `{"status":"400","errmsg":null}` —— 没有提示，只能靠对比试。

**另一个坑**：`encrypted*` 系列接口要求请求带 `Referer: https://web.chelaile.net.cn/`，否则同样返回 400。这一点在 curl 复现时最容易踩到。

### 5.3 加密

`/api/bus/*!encrypted*.action` 返回 `data.encryptResult`（base64），解密方式：

```
算法  AES-256-ECB / PKCS#7
密钥  32 字节 ASCII，见 packages/protocol/src/config.ts 的 AES_KEY
```

验证代码（Node）：

```ts
import { aesEcbDecrypt, base64ToBytes, AES_KEY } from "@chelaile/protocol";
const json = JSON.parse(new TextDecoder().decode(
  aesEcbDecrypt(new TextEncoder().encode(AES_KEY), base64ToBytes(encryptResult))
));
```

一条真实快照已放进 `tests/fixtures/station-detail.encrypted.json`，单元测试会校验它能解出「东堤中路」站点。

### 5.4 签名（可跳过）

`cryptoSign = md5(按顺序拼接 "k=v&k=v" + 盐)`，盐为固定字符串（见 `SIGN_SALT`）。**实测服务端不校验**：传 `deadbeef…` 依然返回 `status=00`。因此本项目的签名实现只用于「对拍/兼容」，不参与鉴权。

### 5.5 端点清单

完整表格见 [02-协议参考.md](02-协议参考.md)。核心五个：

| 端点 | 加密 | 用途 |
| --- | --- | --- |
| `/cdatasource/citylist` | 否 | 城市列表 / 定位城市 |
| `/api/bus/cityLineList` | 否 | 城市全部线路（**忽略 lineName，需本地过滤**） |
| `/api/bus/line!lineRoute.action` | 否 | 站序 + 轨迹 |

## 6. 静态分析中确认不到的（诚实记录）

1. **`stnStates` 的真实字段形态**：线上所有查询都发生在北京时间凌晨（03:20–04:20），全部线路 `buses=[]`、`stnStates=[]`。只能确认“有车时才有值”，具体字段（`order/time/distance` 还是 `buses[]` 嵌套）以兼容方式处理，见 `models.ts#collectBuses`。
2. **搜索接口**：`encryptedNSearch` 传 `keyword` 返回 `status=01 无结果`，参数组合未摸全（可能需要 `cityState`/`sId` 等）。当前用 `cityLineList` 全量 + 本地过滤替代，效果足够。
3. **业务 dex 的代码逻辑**：未脱壳，因此“为什么这么设计”“客户端做了哪些缓存/降级”这些只能从外部行为推断（如 `refreshInterval` 字段说明刷新节奏由服务端下发）。
4. **广告/支付/账号**：本开源版一律不实现，避免触碰需要授权的个人数据。

## 8. 风险与边界

- **接口稳定性**：无 SLA、无文档，随时可能加签/改字段。本项目已把所有协议细节收敛到 `packages/protocol`，升级时只需改一处。
- **频率**：BFF 默认对到站查询做 15 秒 TTL + 请求合并；请不要把 TTL 调到 0 去压测对方服务器。
- **数据权利**：所有线路/站点/到站数据版权归原公司；本项目只做“协议层面的等价客户端”，不缓存、不再分发数据。
- **合规**：见 [04-合规与免责.md](04-合规与免责.md)。
